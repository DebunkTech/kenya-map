# Boundary data

Generated by `npm run data` (`scripts/build-data.mjs`). Don't hand-edit the
files in this folder — re-run the pipeline instead, and edit the script if
the output needs to change.

- `counties.topojson` — 47 counties
- `constituencies.topojson` — 290 constituencies, each with a `county_code`
- `wards/{county_code}.topojson` — 1,450 wards, split per county for lazy
  loading, each with `county_code` and `constituency_code`
- `codes.json` — a flat list of every area (`code`, `name`, `level`, and
  parent codes), for looking up codes when preparing your own datasets.
  **This file is for you, at data-prep time — the `<KenyaMap />` component
  itself never fetches or loads it.**

Every feature's properties are normalised to just `code`, `name`, and parent
codes. Codes are zero-padded strings: 3 digits for counties and
constituencies, 4 for wards.

## Why counties and constituencies are built by dissolving wards

Every level's *geometry* comes from the same ward layer now. Counties and
constituencies are built by dissolving the (simplified) ward polygons up by
`county_code` and `constituency_code` — not from counties.zip/
constituencies.zip's own shapes. This means a county's edge is made of the
exact same simplified ward edges as the wards inside it: there is no
separately-digitized, separately-simplified county or constituency shape
that only approximately lines up with the wards beneath it. All three
levels align exactly when drilling down.

counties.zip and constituencies.zip are still downloaded and used, but only
for their **names and codes** (`COUNTY_COD`/`COUNTY_NAM`,
`CONST_CODE`/`CONSTITUEN` — both already clean, unique, official IEBC
numbers; constituency codes are a contiguous 1–290 range). Constituencies.
zip's *geometry* is also used, but only internally, as the target for the
spatial join described below — it is never shipped in
`constituencies.topojson`. Counties.zip's geometry isn't used at all.

An earlier version of this pipeline instead used counties.zip/
constituencies.zip's own boundaries for those two levels, and only wards
came from a separate dataset — edges *approximately* lined up (both
sources are IEBC/election-based) but weren't identical, since they were
independently digitized and simplified. Dissolving wards up removes that
gap entirely, at the cost of heavier counties/constituencies files, since
their outer edges now carry the same level of vertex detail as the wards
along them (see file sizes below).

**Coordinate quantization caveat.** counties.topojson, constituencies.
topojson, and each wards/{code}.topojson are still separate files (for lazy
loading), and TopoJSON quantizes coordinates to a grid that's auto-picked
per file from that file's own bounding box. So although the *dissolve*
gives every level identical source coordinates at shared borders, each
file's independent quantization step could in principle snap a shared
vertex to a very slightly different position. Measured worst case: ~7m
(counties/constituencies) to ~5m (wards) — this pipeline verified it, see
`scripts/build-data.mjs` step 7. That's below one screen pixel at any zoom
level this map is used at (a whole-country SVG view), so it isn't fixed;
disabling quantization entirely (`no-quantization`) would make it
byte-exact but roughly **3.7x** the file size for a difference nobody will
see. Worth revisiting if this data is ever used somewhere that needs
literal byte-identical coordinates.

## Payload size: simplification level, and why counties+constituencies aren't combined into one file

The base simplification applied to the shared ward layer (before
dissolving counties/constituencies from it — see above) is **3%** of
source points, not 10%. Measured before adopting it: county/constituency/
ward area stays stable to 4-5 significant figures even at 2%, and every
level keeps its exact feature count (47/290/1,450) with zero unrepaired
topology intersections from 10% all the way down to 2%. 3% was chosen as a
comfortable, non-maximal margin under the ~100 KB gzipped initial-load
target, rather than the most aggressive setting tested:

| File | 10% (previous) | 3% (current) |
|---|---|---|
| `counties.topojson` | 257 KB / 81 KB gz | 87 KB / 28 KB gz |
| `constituencies.topojson` | 561 KB / 173 KB gz | 213 KB / 65 KB gz |
| `wards/*.topojson` (47 files) | 1,397 KB / 462 KB gz | 639 KB / 206 KB gz |
| `codes.json` (unaffected) | 221 KB / 17 KB gz | 221 KB / 17 KB gz |
| **Total** | **~2.4 MB / ~733 KB gz** | **~1.16 MB / ~316 KB gz** |

**Combining counties+constituencies into one shared-arc TopoJSON was tried
and works, but isn't used.** `mapshaper -i counties... -i constituencies...
-o format=topojson target=counties,constituencies combine-layers` produces
one file with two objects sharing an arc pool — and because counties
dissolve from the same wards as constituencies, almost every county arc is
already present in the constituencies arc set, so the combined file is only
marginally bigger than constituencies.topojson alone (measured at 10%:
568 KB / 176 KB gz combined, vs. 818 KB / 254 KB gz for the two separate
files added together — arc sharing saves real bytes).

It isn't adopted as the shipped format because it works against the actual
goal: **`<KenyaMap />`'s first paint only needs counties**, exactly like it
only needs one county's wards at a time. Combining forces constituencies
into that critical initial fetch (176 KB gz combined vs. 28 KB gz for
counties alone at 3%), even though constituencies aren't needed until a
user clicks a county. The component instead fetches
`constituencies.topojson` lazily on the first county click — the same lazy
pattern already used for `wards/{county_code}.topojson` — so the initial
load stays at counties.topojson alone.

## How wards are linked to constituencies

The wards dataset has no constituency code of its own — only a free-text
`subcounty` name that doesn't map 1:1 to the 290 constituencies (302 unique
subcounty names exist in the source). Each ward's `constituency_code` (and
`county_code`) is instead assigned by a spatial join: testing the ward's
centroid for containment in each constituency polygon from constituencies.
zip (`d3.geoContains`).

One ward's centroid falls outside every constituency polygon (likely a
concave-boundary edge case): **"Moyale Township"**, assigned instead to the
nearest constituency by centroid distance — **Moyale (code 045)**. Worth a
visual spot-check if you're auditing this pipeline's output.

Ward codes themselves are assigned by the pipeline (sequential, sorted by
county → constituency → name) since the source has no usable official
code — they are **not** official IEBC ward codes, unlike county and
constituency codes.

## Known data quality quirks

- **Sliver artifacts filtered.** The counties and constituencies shapefiles
  each contain a handful of tiny, unattributed polygons (code `0`, empty
  name) alongside the real records — digitizing artifacts, not real areas.
  The pipeline drops any feature with `COUNTY_COD` / `CONST_CODE` equal to 0.
- **Reversed ring winding.** Every feature in all three source shapefiles
  comes out of the shapefile→GeoJSON conversion with its polygon rings
  wound backwards relative to the GeoJSON/RFC 7946 convention (clockwise
  exterior rings, an Esri Shapefile convention that wasn't flipped on
  conversion). Left alone, this breaks every spherical predicate in d3-geo
  (`geoContains`, `geoCentroid`, ...) — d3-geo reads such a polygon as
  covering the *entire sphere minus* the real area, which silently broke
  the ward→constituency spatial join in an early version of this pipeline
  (every ward matched whichever constituency happened to be first in the
  list). The pipeline detects and corrects this (`scripts/lib/geometry.mjs`)
  before doing anything geometry-aware.
- **Simplify before/after clean order matters.** Simplifying first produced
  hundreds to thousands of self-intersections mapshaper couldn't repair.
  Running `-clean` *before* `-simplify` (to remove pre-existing tiny
  slivers first) eliminates this — the pipeline does
  `-clean -simplify 10% keep-shapes -clean` on the ward layer before
  dissolving it up.
- **Misspelled names in the source.** Two are known: the county spelled
  "ELEGEYO-MARAKWET" (commonly spelled "Elgeyo-Marakwet"), and the
  constituency spelled "WEBUTE WEST" (should be "Webuye West" — its
  neighbour in the same file is correctly spelled "Webuye East"). The
  pipeline only fixes casing/spacing, never spelling, so both are shipped
  as-is — correct them in the pipeline if you'd rather ship the common
  spelling.
- **Ward name "Ward" suffix.** 1,364 of 1,450 source ward names end in
  " Ward" (e.g. "Airport Ward"), which the pipeline strips as redundant
  (each feature already has `level: "ward"`). A handful of names don't have
  it, and one ("Rurumaward" in Kilifi) has "ward" run directly into the name
  with no space or separator — left as-is, since splitting it would mean
  guessing where the join happened rather than reading it off the source.

## `data/raw/ken_admin_boundaries.xlsx`

Not used by the pipeline, kept in `data/raw/` (git-ignored) for reference.
This is a plain attribute gazetteer (OCHA COD-AB export, dated 2019-10-31)
with **no polygon geometry at all** — just names, P-codes, and centroid
points for admin0 (country), admin1 (47 counties) and admin2 (290 units).
It describes KNBS administrative sub-counties rather than IEBC electoral
constituencies, but in Kenya the two were redrawn 1:1 after the 2010
constitution, and it functions as one: same count (290) and mostly the same
names as the constituencies in this pipeline's output.

Cross-checking its 290 names against this pipeline's 290 constituency names
found 276 exact matches; the remaining 14 are explained by two typos already
noted above (in whichever file has the error), and by real historical
splits/renames between the two sources' vintages (e.g. "Dagoretti" here is
"Dagoretti North"/"Dagoretti South"; "Mbeere" is "Mbeere North"/"Mbeere
South"; "Suba" is "Suba North"/"Suba South") — not data corruption. It was
a useful independent sanity check on the constituency data, but can't supply
boundaries.

## Re-running the pipeline

`npm run data` downloads the three source zips into `data/raw/` (skipped if
already present — delete `data/raw/*.zip` to force a re-download), then
regenerates every file in this folder. `data/raw/` is git-ignored.
